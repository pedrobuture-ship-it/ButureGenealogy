# PROMPT 8 — Motor de acasalamento MVP

Agora implemente a primeira versão do coração do software:

# Acasalamentos

IMPORTANTE:

O motor deve ser transparente, determinístico e auditável.

Não use IA/LLM para escolher touros.

Não invente modelos científicos.

O motor somente poderá calcular uma característica quando existir informação suficiente e metodologia explicitamente suportada.

Fluxo:

1. usuário escolhe uma matriz;
2. escolhe os touros candidatos;
3. escolhe um perfil de objetivo;
4. define pesos;
5. sistema valida compatibilidade das avaliações;
6. aplica filtros;
7. calcula os componentes permitidos;
8. gera ranking;
9. salva um snapshot completo do cálculo.

Perfis iniciais podem ser:

- Personalizado;
- Demonstração Corte;
- Demonstração Leite.

Os perfis de demonstração devem estar explicitamente marcados:

`DEMO — NÃO REPRESENTA RECOMENDAÇÃO ZOOTÉCNICA VALIDADA`

Permita editar todos os pesos.

O motor deverá possuir pipeline semelhante a:

```text
Candidate
   ↓
Validation
   ↓
Hard Filters
   ↓
Trait Compatibility
   ↓
Normalization
   ↓
Weighted Components
   ↓
Complementarity
   ↓
Penalties
   ↓
Final Score
```

Crie interfaces Go bem separadas para cada etapa.

Exemplo conceitual:

```go
type ScoringComponent interface {
    Calculate(ctx CalculationContext) ComponentResult
}
```

Cada `ComponentResult` deve guardar:

- nome;
- valor de entrada;
- transformação;
- peso;
- contribuição;
- fonte;
- explicação;
- warnings.

NUNCA faça algo como:

```text
score = número mágico
```

sem registrar de onde veio.

Para normalização:

- quando houver percentil válido e comparável, permita uma transformação documentada;
- quando houver parâmetros populacionais fornecidos pelo dataset, prepare suporte a normalização estatística;
- se não houver parâmetros suficientes, informe que não é possível calcular aquela parte.

Não converta avaliações de bases incompatíveis como se fossem equivalentes.

Se matriz e touro estiverem em avaliações incompatíveis:

```text
⚠ Comparação genética não suportada entre essas bases.
```

Para o MVP, é preferível retornar `não calculável` do que produzir um número falso.

Crie:

- ranking;
- Top candidatos;
- filtros;
- warnings;
- snapshot;
- versão do motor;
- dataset IDs e versões utilizados.

Adicione muitos testes unitários com dados sintéticos.

# CONCEITO FINAL DO PRODUTO

Estamos construindo uma plataforma desktop, local-first, aberta e auditável para planejamento de melhoramento genético bovino.

O sistema deve permitir que um produtor, técnico, veterinário ou zootecnista:

```text
cadastre o rebanho
        ↓
mantenha pedigree
        ↓
registre fenótipos
        ↓
instale datasets/bibliotecas
        ↓
importe avaliações genéticas
        ↓
mantenha touros e estoque de sêmen
        ↓
escolha uma matriz
        ↓
defina objetivos genéticos
        ↓
compare touros compatíveis
        ↓
receba ranking
        ↓
abra "Ver cálculo"
        ↓
entenda exatamente como a conclusão foi produzida
```

Existem quatro princípios fundamentais.

## 1. LOCAL-FIRST

O rebanho pertence ao usuário.

O software deve continuar funcionando offline.

A ausência de internet não pode impedir:

- cadastro;
- consulta;
- pedigree;
- análises com dados já disponíveis;
- acasalamentos;
- relatórios;
- consulta a cálculos anteriores.

Serviços externos são complementares.

---

## 2. DATASETS COMO BIBLIOTECAS

O conhecimento genético não deve ficar hardcoded.

O sistema deverá evoluir através de datasets/bibliotecas instaláveis.

Conceitualmente:

```text
                 BIBLIOTECAS
                      ↓
                 TRAITS
                      ↓
               MOTOR GENÉTICO
                      ↓
     ┌────────────────┼────────────────┐
     ↓                ↓                ↓
 PEDIGREE         FENÓTIPO         GENÉTICA
     └────────────────┼────────────────┘
                      ↓
                 ACASALAMENTO
                      ↓
                    SCORE
                      ↓
                VER CÁLCULO
```

A distribuição oficial deverá utilizar somente datasets cuja licença permita a utilização pretendida.

Se forem redistribuídos junto ao programa, a licença deverá permitir redistribuição.

Dados simplesmente “gratuitos para consultar” não devem ser considerados automaticamente livres para redistribuição.

Usuários poderão instalar bases adicionais pelas quais tenham autorização.

---

## 3. NÃO SER CAIXA-PRETA

Qualquer recomendação importante deve possuir:

`Ver cálculo`

O sistema precisa conseguir responder:

### Qual touro foi recomendado?

Ranking.

### Por quê?

Explicação.

### Como chegou àquela nota?

Detalhamento matemático.

### Quais dados foram utilizados?

Dataset + versão + valores.

### De onde vieram?

Proveniência.

### Qual versão do algoritmo fez isso?

Engine version.

---

## 4. NÃO INVENTAR CIÊNCIA

Se determinada comparação não puder ser feita corretamente:

```text
Não calculável com os dados disponíveis.
```

é uma resposta válida.

Nunca trocar isso por um número aparentemente preciso.

DEP, EPD, EBV, PTA, fenótipos e índices não devem ser tratados automaticamente como equivalentes.

Avaliações de diferentes programas não devem ser comparadas sem metodologia válida.

---
